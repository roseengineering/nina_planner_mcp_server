# Multi-target night loop

Triggered by an interval check or a `RUN-FINISHED` event. Safety checks come from the `safety-interrupt-recovery` skill.

1. Read `PLAN.md` (the user's living wishlist) and `PROGRESS.md` fresh each time.
2. Read the `Rules` section of `PLAN.md` for `min_altitude` (default 30), `horizon_offset_degrees` (default 2), and tie-break order. Evaluate each un-imaged candidate: compute its current altitude from its coordinates (RA/Dec in the `PLAN.md` entry) and the site location (`get_site_profile`).  To most effectively compute these constraints load the desired sequence into NINA and call `get_sequence_state` to get the resulting values.  Only stop a running sequence to do this if it is not yet imaging or is done.
3. Pick the best candidate now: highest priority, then highest current altitude, then earliest available (or the tie-break order in `PLAN.md` Rules). **Never interrupt an acquisition in progress to switch targets.** A sequence does *not* finish when its target finishes — its End area waits until the enclosure goes unsafe or sunrise, so `sequence-finished` only fires at dawn and is not a mid-night signal. Re-selection is driven by the run bracket, not by segment events. `load_sequence` composes the whole request list into one N.I.N.A. sequence bracketed by `RUN-STARTING: N steps` in the Start area and **`RUN-FINISHED: N steps complete`** at the head of the End area. The End area is reached only when the Target area has nothing left — entries skipped as already complete, window-passed flats and steps queued behind the finished one all resolve themselves — so `RUN-FINISHED` really does mean the run is done and the scope is idling in the End container before park/warm; the stow emits neither event, so a stow can never read as a finished run. On `RUN-FINISHED`: if a viable list exists, `stop_sequence()` (that is not interrupting an observation), then load and start it; if nothing is viable, leave the sequence alone — the End area is already parking and warming, which is the stow, so step 4's report can proceed without loading one. Segment events are read-only telemetry: each step emits `ACQUISITION-STARTING` / `ACQUISITION-FINISHED: [{kind}] {target} [{plan_id}]` with `kind` in `light`, `dark`, `bias`, `dawn flats`, `dusk flats`, `-N` in the token marking a mosaic pane and a bare token a single-pointing plan or plan-level calibration — that is how you know what N.I.N.A. is working on right now, and **never** a reason to stop a sequence or re-select: the list you wrote runs to completion. On the first live run, verify that both the run bracket and the segment messages actually surface in `get_events`; if they only land in the application log, use `get_logs` instead.
4. If no candidate is viable (none above `min_altitude` + `horizon_offset_degrees`): the night is over. Write `report.md` (overwriting any previous one) — night date, targets and frames actually completed, calibration counts, failures/interventions, wrap-up — using `PROGRESS.md` plus `get_events`/`get_logs`. Append a `PROGRESS.md` entry ("no targets above floor / night over"). Then stow: check `get_sequence_state` first — if a sequence is running, let it finish rather than loading a stow sequence over it (on `RUN-FINISHED` it is running in its End area and already parking and warming, so leave it alone); only load `load_sequence()` and `start_sequence()` when nothing is running. If `PLAN.md` is edited later, the next trigger re-evaluates.
5. For the chosen target: verify safety (`is_safe=true` and weather OK) before starting. If a plan JSON is referenced, load it; otherwise generate one via `write_plan_file` (using coords/filter/count from `PLAN.md`, or sensible defaults). For a mosaic, generate the multi-pointing plan with `write_mosaic_plan(plan_path, mosaic_csv)` (one pointing per pane), then acquire it pane by pane: call `get_plan_progress(file_path)` and `load_sequence(request=[{"plan": file_path, "action": "light", "pointing_index": N, "mode": "remaining"}])` followed by `start_sequence()` for the first pane that is not `complete`. Keep the target selected until every pane reports `complete`; never switch targets mid-mosaic. For a single-pointing plan, `load_sequence(request=[{"plan": file_path, "action": "light"}])` then `start_sequence()` — `load_sequence` only loads, never starts. `request` is always a **list** (it defaults to an empty list, which is the stow): one `start_sequence()` runs every step in order, entries already complete are skipped and reported, and the End area always parks and warms. Note the interaction with step 3: a running list has no re-selection point inside it — `RUN-FINISHED` arrives once, at the end — so commit a list only when the order is already decided (remaining panes, then calibration); load one target at a time when you do want to re-evaluate between targets, since the end of each such list is its own re-selection point.
6. Append a `PROGRESS.md` entry: target chosen, altitude at start, why it was chosen over others, mosaic pane index and remaining panes if applicable, any caveats. Record completion in `PROGRESS.md` (leave `PLAN.md` untouched — the user may be editing it).
7. Confirm the sequence is running via `get_sequence_state`, then await the next trigger.
